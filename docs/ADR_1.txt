# ADR-001: Selección del Stack Tecnológico (Flutter, Dart y Firebase)

**Fecha:** 2026-10-01
**Estado:** Aceptado
**Prioridad:** Alta (Crítica para el inicio y viabilidad del proyecto)
**Decisores:** Equipo de Desarrollo de CampusBites
**Consultados:** No especificado

---

## Contexto
Se requiere desarrollar una aplicación móvil multiplataforma (Android e iOS) para estudiantes universitarios. La app necesita renderizado fluido para animaciones complejas (deslizamiento de tarjetas estilo Tinder), sincronización en tiempo real para ubicación y estados de citas, e integración de notificaciones push de alta fiabilidad.

---

## Decisión
**Decidimos:** Utilizar Flutter como framework de desarrollo móvil con Dart como lenguaje único, adoptando el ecosistema de Firebase (Cloud Firestore, Authentication y Cloud Messaging) como infraestructura backend.

---

## Justificación
1. **Rendimiento gráfico y animaciones:** Flutter compila a código máquina nativo, ofreciendo un rendimiento de 60/120 fps crítico para animaciones de gestos (swiping).
2. **Desarrollo unificado y fuertemente tipado:** Dart ofrece tipado fuerte (facilitando la generación de código con IA) y permite utilizar un solo lenguaje para la UI y la lógica del cliente.
3. **Sincronización de base de datos en tiempo real:** La arquitectura de escuchadores (*listeners*) de Cloud Firestore permite que los cambios de estado (ubicación, citas) se reflejen instantáneamente sin recargar la app.
4. **Notificaciones de baja latencia:** Firebase Cloud Messaging (FCM) ofrece integración nativa directa con la menor latencia posible para alertas críticas de la aplicación.
5. **Autenticación simplificada:** Firebase Authentication facilita la configuración necesaria para la validación de dominios institucionales (`.edu`).

---

## Consecuencias

### Consecuencias positivas ✅
- **Desarrollo Unificado:** Se optimiza el tiempo manteniendo un solo lenguaje (Dart) para toda la interfaz gráfica y la lógica multiplataforma.
- **Infraestructura Serverless:** Sin necesidad de administrar servidores dedicados; Firebase escala automáticamente durante las horas pico de uso en los recesos universitarios.

### Consecuencias negativas ❌
- **Costos de Lectura/Escritura:** Dependencia estricta del modelo de cobro de Firestore, lo que exige estrategias complejas para no agotar la cuota gratuita con la sincronización del mapa.

### Acciones derivadas 📌
- [ ] Configurar el proyecto en Firebase y enlazarlo con el cliente móvil mediante CLI (`flutterfire`).
- [ ] Diseñar el esquema NoSQL orientado a minimizar operaciones de lectura/escritura (desnormalización de datos).
- [ ] Implementar y probar las reglas de seguridad de Firebase Auth para limitar registros a correos estudiantiles.

---

## Alternativas Consideradas

### Alternativa 1: React Native + Supabase
**Descripción:** Construir el frontend con React Native respaldado por el backend open source de Supabase.
**Razón para descartarla:** Aunque es una opción robusta, requiere integrar y mantener bibliotecas de terceros adicionales para manejar notificaciones push y mapas nativos de manera fluida, rompiendo la cohesión que sí ofrece el ecosistema propio de Google (Flutter + Firebase).
